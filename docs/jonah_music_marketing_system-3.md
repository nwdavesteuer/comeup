# Project: Fanbase Builder - AI-Powered Growth Platform for Emerging Artists
## Personalized Strategy Based on Sub-Genre Benchmarks

**Mission**: Build a platform that tells emerging artists EXACTLY what to do to grow their fanbase - when to release music, what content to post, and how to maximize engagement - based on data from successful artists in their specific sub-genre.

**Core Value Proposition**: "It predicts what will work before I waste time creating content" - using actual data from artists like you who have succeeded to give personalized recommendations.

**Success Metric**: Within 1 month of following guidance, artists see 3x increase in Spotify and Instagram engagement rate.

## Technical Architecture

### Platform Stack

**Frontend:**
- React (web app) - Primary interface
- Responsive design (works on mobile, but not native app initially)
- Dashboard, onboarding, recommendations, calendar views

**Backend:**
- FastAPI (Python) - API layer
- PostgreSQL - All data storage
- Redis - Caching for real-time features
- APScheduler - Background jobs (data collection, prediction generation)

**AI/ML Layer:**
- Claude API - Generate tactical recommendations, explain strategy, weekly insights
- Scikit-learn - Predictive models (engagement prediction, growth forecasting)
- Pandas - Data analysis and pattern recognition

**Integrations:**
- Spotify Web API (public data) + Spotify for Artists OAuth (partner artists)
- Instagram Graph API (requires business accounts)
- YouTube Data API
- Optional: TikTok API (if approved)

**Hosting:**
- Railway or Render ($20-50/month)
- PostgreSQL cloud instance
- AWS S3 for file storage (artist music uploads)

**Development Tools:**
- Cursor with Claude Code - Primary development environment
- GitHub - Version control
- Postico/TablePlus - Database management
- Postman - API testing

### Data Architecture

**Core Tables:**

**artists**
- artist_id, user_id, artist_name, spotify_id, instagram_handle, tiktok_handle
- sub_genre, comparable_artists[], onboarding_complete, created_at

**benchmark_cohorts**
- cohort_id, sub_genre_name, artist_ids[], created_at
- Used to group similar artists for benchmarking

**daily_metrics** (Time-series data)
- metric_id, artist_id, date, platform, metric_name, value
- Stores all metrics over time (followers, listeners, engagement)

**content_posts**
- post_id, artist_id, platform, posted_at, content_type, url, caption
- scheduled_for (if future), status (scheduled/published)

**content_performance**
- performance_id, post_id, measured_at, likes, comments, saves, shares, reach
- engagement_rate, spotify_traffic_lift

**recommendations**
- recommendation_id, artist_id, week_start_date, generated_at
- recommendations_json (structured data with all tactical advice)
- followed (boolean), actual_vs_predicted_variance

**benchmark_patterns** (Derived insights)
- pattern_id, sub_genre, pattern_type, pattern_data_json
- Examples: "optimal_posting_times", "content_type_performance", "growth_rates"

### Intelligence Engine Architecture

**Weekly Recommendation Generator:**
```
Input:
- Artist's current metrics (last 30 days)
- Benchmark patterns for their sub-genre
- Artist's historical performance (if exists)
- Unreleased music timeline

Process:
1. Analyze current state vs. benchmarks (gap analysis)
2. Identify what's working (if personalized data exists)
3. Generate tactical recommendations using Claude API:
   - Music release timing
   - Content calendar (5 posts with specifics)
   - Growth predictions
   - Strategic context
4. Store recommendations in database
5. Display in dashboard

Output:
- Structured weekly action plan
- Predicted outcomes with confidence intervals
- Strategic explanations for each recommendation
```

**Prediction Models:**
```
Engagement Prediction Model:
- Input: content_type, posting_time, caption_style, artist_baseline, benchmark_avg
- Output: predicted_engagement_rate, confidence_score

Growth Forecast Model:
- Input: current_metrics, planned_content_frequency, release_schedule, benchmark_trajectories
- Output: predicted_growth_30_days, predicted_growth_90_days, key_drivers

Content Type Performance:
- Input: artist's content history (if exists), benchmark patterns
- Output: ranked_content_types, optimal_frequency, best_practices
```

## Risk Mitigation

### Technical Risks:

**Risk: Benchmark data quality insufficient**
- Mitigation: Collect 4 weeks of data before launch (not just 2)
- Fallback: Use research-based best practices if data thin

**Risk: Spotify API rate limits**
- Mitigation: Implement caching, batch requests, exponential backoff
- Fallback: Reduce tracking frequency if needed

**Risk: Claude API costs too high**
- Mitigation: Cache recommendations, only regenerate when needed
- Current usage: ~$0.50 per artist per week = $10/month for 20 artists

**Risk: Recommendation accuracy too low**
- Mitigation: Start with benchmarks (60-70% accuracy acceptable)
- Improvement: Accuracy increases as personalized data accumulates

### Product Risks:

**Risk: Artists don't follow recommendations**
- Mitigation: Make recommendations extremely specific and easy to follow
- Engagement: Send reminders, celebrate when followed

**Risk: Results take too long to see**
- Mitigation: Set expectations (4 weeks), show leading indicators
- Early wins: Highlight improved engagement rates before growth shows

**Risk: Sub-genre matching inaccurate**
- Mitigation: Manual override option, artist can adjust cohort
- Validation: Show artist their cohort, let them confirm/reject

### Business Risks:

**Risk: Hard to get artist partnerships for benchmark data**
- Mitigation: Start with Jonah's connections only (lower target: 5 artists)
- Fallback: Rely more on public data + Kiss Bang's data

**Risk: Platform too complex for artists**
- Mitigation: Extreme simplicity in UI, tooltips everywhere
- Onboarding: Hand-hold first users, iterate based on feedback

### The Attribution Challenge (And How to Solve It)

**The Problem:**
You can't directly link an Instagram post to specific Spotify streams. The platforms don't talk to each other.

**The Solution: Time-Based Correlation**
```python
def calculate_spotify_traffic_lift(post_id):
    """
    Estimate stream increase driven by a social post
    """
    post = get_post(post_id)
    artist_id = post.artist_id
    post_date = post.posted_at.date()
    
    # Get baseline: average daily streams for 3 days before post
    baseline = avg_daily_streams(
        artist_id=artist_id,
        start=post_date - timedelta(days=3),
        end=post_date - timedelta(days=1)
    )
    
    # Get lift: total streams for 2 days after post
    post_period_streams = sum_daily_streams(
        artist_id=artist_id,
        start=post_date,
        end=post_date + timedelta(days=2)
    )
    
    # Calculate lift above baseline
    expected_streams = baseline * 2  # 2 days
    actual_lift = post_period_streams - expected_streams
    
    return max(0, actual_lift)  # Don't show negative
```

**What this gives you:**
- "This post was followed by +200 streams above your baseline"
- Not perfect attribution, but directionally correct
- Good enough for insights and recommendations

**Edge cases it handles:**
- If artist has release or playlist add, spike affects all posts that week
- You can flag anomalies: "Unusually high activity this week"
- Compare multiple posts in same period to see which drove more

#### Understanding the Architecture (5 minutes to read)

Your application has **three separate pieces** that work together:

```
FRONTEND (React)              BACKEND (FastAPI)           DATABASE (PostgreSQL)
Running on Vercel      ←→     Running on Railway     ←→   Hosted by Railway
Your user interface           Your business logic         Your data storage
```

**Key concept:** Frontend and Backend are separate applications that communicate via HTTP API calls. This is modern web architecture.

**Why this matters:**
- You can update frontend without touching backend (and vice versa)
- Frontend can be static files (fast, cheap to host)
- Backend handles all sensitive operations (database, API keys, OAuth)
- Multiple frontends (web, mobile) can use same backend
